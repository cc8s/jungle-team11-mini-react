# patch 트러블슈팅

TDD Red 단계에서 실패한 테스트와 원인, 수정 내용을 기록한다.

## EC-025, EC-026 외부 코드가 부모 맨 앞에 노드를 끼워 넣어도 MOVE·ADD는 관리하는 노드의 순서를 지킨다

- **발견 경위**: 북마크가 "위치(자식 index)로 찾는 방식"보다 외부 DOM 변경에 견고한지 실제 브라우저에서 확인했다. Phase 2 곡 목록(`ul`) 맨 앞에 `<aside>`를 끼워 넣고 song_2의 "아래로"를 누르자, State는 맞는데 화면 순서가 song_3, song_1, song_2로 틀렸다(기대: song_1, song_3, song_2). 오류 없이 화면과 State가 어긋났다.
- **증상 (Red)**

  ```
  EC-025  actual: [ 'c', 'a', 'b' ]   expected: [ 'a', 'c', 'b' ]
  EC-026  actual: [ 'x', 'a', 'b' ]   expected: [ 'a', 'x', 'b' ]
  ```

- **원인**: 기존 노드는 북마크로 찾지만, `ADD`와 `MOVE`의 넣을 자리는 `parent_dom_node.childNodes[operation.index]`로 셌다. Virtual DOM 트리는 외부 노드를 모르므로, 끼워 넣은 노드만큼 index가 밀려 한 칸 앞에 들어갔다.
- **수정**: diff가 `ADD`·`MOVE`에 새 순서에서 바로 앞에 오는 형제(`previous_node`, 맨 앞이면 `null`)를 함께 싣는다. index 오름차순으로 적용하므로 앞 형제는 이미 제자리에 있다. patch는 그 형제의 DOM을 북마크로 찾아 `nextSibling` 앞에 넣고, 맨 앞이면 부모의 첫 자식 앞에 넣는다. `previous_node`가 없는 연산(직접 만든 연산)은 예전처럼 index로 센다.
- **확인**: 무작위 트리 300쌍에 외부 노드를 아무 곳에나 끼워 넣는 EC-027을 추가했다. 수정 전 코드에서는 실패하고 수정 후 통과한다. 기존의 무작위 patch 테스트(EC-013, EC-014)도 그대로 통과한다.
- **수정 중 만난 실패**: EC-026의 두 번째 patch에 화면에 그려진 트리 대신 같은 모양으로 새로 만든 트리를 이전 트리로 넘겨 "북마크된 DOM 노드가 없습니다"가 났다. 테스트가 실제로 그린 트리 객체를 넘기도록 고쳤다(구현 문제가 아님).
